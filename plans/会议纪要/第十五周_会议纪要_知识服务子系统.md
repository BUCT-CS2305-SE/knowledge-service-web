## 四、技术/协作决策

- **决策1（认证体系统一）**：三个子系统（知识服务/知识问答/后台管理）统一采用 Bearer Token 认证方案。Token 由后台管理子系统（子系统5）统一签发，知识服务子系统（子系统2）和知识问答子系统（子系统3）共享同一认证体系。登录入口统一在本子系统，登录成功后 token 存储至 localStorage，跨子系统请求均携带 `Authorization: Bearer <token>` 请求头。

- **决策2（问答页面设计）**：新增 `/qa` 路由，QA 页面参考 ChatGPT 对话式交互风格，支持以下功能：（1）自然语言输入文物相关问题；（2）问答结果以卡片形式展示，包含相关文物预览、知识图谱三元组、置信度标注；（3）问答历史记录可回溯；（4）答案质量反馈按钮（有用/无用）。由田亮负责 UI 开发，郭展宏负责接口对接。

- **决策3（数据迁移策略）**：用户收藏和评论数据从 localStorage 迁移至后台数据库时，采用"增量同步"模式——首次全量导入后，后续仅同步新增或修改的记录。迁移过程保留客户端本地副本作为回滚备份。

- **决策4（接口规范对齐机制）**：由赵子皓负责汇总三个子系统接口规范不一致之处，形成《跨子系统接口规范对齐表》文档，统一提交至课程负责人协调。主要包括：字段命名统一（camelCase vs snake_case）、分页参数统一（page/size vs offset/limit）、错误码规范统一。

- **决策5（联调优先级排序）**：联调工作按以下优先级推进——P0：用户认证联调（阻塞所有需登录的功能）；P1：文物数据接口联调（核心功能依赖）；P2：知识问答接口联调（新增功能）；P3：数据迁移与统计看板对接（优化类功能）。

## 六、其他讨论内容

1. **关于教师反馈的改进方向**：小组汇报后教师提出了以下改进建议，作为联调阶段的工作重点：（1）当前系统各子系统间的衔接不够紧密，建议在知识服务子系统中增加与知识问答子系统的交互入口（如从文物详情页一键跳转至问答页，预填该文物相关问题）；（2）登录认证应统一使用后台管理子系统的用户体系，避免各子系统独立维护用户数据；（3）数据展示应体现多源融合的特性，而非仅展示单一知识图谱子系统的数据。以上三点已纳入本周联调工作。

2. **关于联调协作机制**：鉴于三个子系统分属不同小组开发，联调过程中容易出现"互相等待"的情况。会议决定：（1）本子系统主动推进联调，不等其他子系统先行改动；（2）在 `authService.ts` 和 `artifactService.ts` 中增加兼容层（Adapter），同时支持 Mock 数据和真实 API，确保单个子系统不可用时不影响其他功能；（3）每周三通过微信群向其他子系统同步联调发现的问题和修复进展，避免信息不对称。

3. **关于知识问答联调的技术方案**：知识问答子系统提供的 API 为 `POST /api/qa/ask`，请求体为 `{ question: string, context?: { artifactId?: string } }`，响应体为 `{ answer: string, confidence: number, relatedArtifacts: string[], triples: Triple[] }`。本子系统需在问答页展示：（1）答案正文（Markdown 格式渲染）；（2）置信度进度条；（3）相关文物卡片（可点击跳转详情页）；（4）知识图谱三元组列表。对于置信度低于 60% 的回答，前端标注"低可信度"提示。

4. **关于文物ID映射问题**：知识问答子系统返回的 `relatedArtifacts` 字段使用的是知识图谱组内部的实体 ID（如 `entity_12345`），而非本子系统的文物 ID（如 `artifact_001`）。需与知识图谱组协商：（1）在 CSV 数据的 `id` 字段保持一致；或（2）知识问答子系统在返回结果中额外提供本子系统兼容的文物 ID；或（3）本子系统维护一份实体 ID→文物 ID 的映射表。优先推荐方案（1），从根本上消除 ID 不一致问题。
